# 私聊中绑定工作搭档与异步交付

首期已实施并在隔离服务验收。本文保留实施时的设计依据，实际交付、真实模型表现和回归结果见[验收记录](../verification/async-bot-partner.md)。

## 产品约定

首期按用户能否在发起委派的会话收到结果验收。B 署名直答和 A 转述均可交付，用户无需指定发言者。点名转述属于表达偏好。

A 是用户正在私聊的 bot，B 是 A 绑定的工作搭档。用户可以给 A 绑定一个已有协作权限的 B。绑定单向生效，B 仍有自己的身份、工作线程、模型、提示词、工具和权限。A 依然可以自己完成任务。普通对话无需先经过分类模型。

| 已确定的决策 | 首期行为 |
| --- | --- |
| 全异步的范围 | 用户在 A 的私聊中发起工作，A 委派给已绑定的 B 时，服务端一律异步受理。A 和用户都无需选择同步或异步。其他队友、咨询、群聊、后台自动化、外部运行时及嵌套委派沿用原协议。 |
| B 正常完成 | B 直接结束工作轮。服务端把最终正文和可交付产物以 B 的身份发布到 A 的原会话，原结果进入 A 的上下文。完成这项工作引起的 A 模型调用数为零。 |
| B 明确通知 A 转述 | 服务端将 B 的原文、产物和转述原因交给 A，安排一次异步回合。转述成功时，主会话展示 A 的最终正文，详情保留 B 的原文和作者。A 转述失败、空答或用户已切换分支时，B 的结果直接送达原请求。 |
| B 需要用户补充资料 | B 在 A 的原会话署名提问，用户定向回复到 B 的原任务。用户在主输入框另聊的话题由 A 接收。授权和审批仍由原来的审批卡及权限检查处理。 |

例：用户对 A 说「告诉我这版改了什么，再让 B 跑一下回归」。A 可以先回答变更，同时委派回归。B 缺少测试分支时在同一会话提问，用户回复该问题后 B 继续执行。测试完成后用户直接看到 B 的测试结论和报告。如果 A 还需结合报告判断能否发布，B 可以请求 A 整理建议。A 转述失败或没有生成可见答复时，原会话自动收到 B 的报告和可交付附件。

## 当前实现与复用边界

- 现有 `coordinate_bots` 已经把工作交给 B 并记录父子委派，普通工作默认按 `resume` 恢复 A。`poll` 需要调用方读取结果，`none` 表达单向发送。运行时既会在子任务结算后写入唤醒项，也会根据子任务是否全部结算来判断父任务是否应恢复。实现时要覆盖两处判定，以及当前要求 A 结束回合等待结果的工具文案。[委派入口](../../server/runtime-coordinator.ts) · [父任务恢复与结算](../../server/runtime/runtime.ts) · [工具回执与提示词](../../server/host/teammate-prompts.ts)
- `post_to_thread` 已经能持久保存发送者、按投递 ID 去重、在接收方下次调用时注入未读内容。目前是活动行，而且等待当前委派的祖先线程会拒绝这种投递。新功能应由委派结算流程把结果交给来源线程，复用来源标记和未读投递思路。保留通用留言工具的目标检查。[线程留言](../../server/host/thread-posts.ts) · [现有留言和上下文用例](../../server/thread-aware-bots.e2e.test.ts)
- 当前父线程对成功结果有活动行预览和指向 B 工作线程的链接。新的聊天正文应取自可公开的最终消息及已经授权交付的附件。运行时的结果摘要、最多 2,000 字符的活动行预览都不能作为唯一正文来源。若某个驱动返回多段正文，绑定其已提交的最后一轮答复，排除推理、工具日志和内部草稿。[结果投递和上下文组装](../../server/index.ts) · [协作附件](../../server/host/handoff-files.ts)
- Novia Server 可借鉴的是保留来源、把后台事实持久化后再投递、单独重试表达。本项目可直接使用已有 bot、委派和线程。首期无需新建聊天人格、工作人格或前置分流器。[Novia 双流契约](../../../novia-server/contracts/02h-dual-flow.md) · [Novia 回执契约](../../../novia-server/contracts/02f-work-inbox.md)

## 绑定、委派与完成责任

1. 在 A 的 bot 设置中提供「工作搭档」，支持选择、替换、清除。沿用现有资料编辑权限和队友可达性判断，候选项说明 B 的名称和职责。服务端同样校验范围、去重和自绑定。旧 bot 缺省为空。建议持久化为有序的目标 bot ID 列表，首期服务端限制最多一个，为未来多搭档保留兼容空间。
2. A 的模型仅需知道绑定的 B 可以承接什么工作，照常调用委派工具。服务端根据来源、目标、工作类型和绑定关系决定投递约定，模型工具参数不提供同步开关。派发成功返回委派 ID 和受理状态；排队不能被描述为已完成。A 可完成用户请求中属于自己的部分，也可在无需补充时结束本轮。
3. 受理时记录 A、B、原会话、原用户请求或消息、委派 ID 和本次交付约定。同一 bot 在不同会话发起的相似工作各自关联。A 当轮结束、切换会话或处理下一条消息后，待交付委派仍由运行时跟踪。原请求可以显示「B 处理中」，A 的输入框和普通新消息继续可用；明确停止整个请求仍能取消它的在途工作。核对已有等待队友时暂缓私聊的设置，给这类委派单独计算阻塞条件。
4. 更换或解除绑定作用于后续委派。在途交付继续认受理时的来源与目标，派发和投递时均核对实际访问权限。若来源线程已删除、访问已撤销或原请求已取消，记录未送达原因，避免投到 A 当前打开的其他线程。快照不能延长已经撤销的权限。

## B 的三个出口

| 事件 | 原会话与运行时行为 |
| --- | --- |
| B 正常结束并给出对用户可见的正文或产物 | 服务端写入署名 B 的普通聊天消息，关联原请求、B 的委派和附件；提交、广播、计入未读并结算。省略重复的结果预览和完成提醒。B 无需调用任何「直接答复」工具。 |
| B 显式请求 A 转述 | 提供限于当前委派的一个动作，例如「请委派方转述」。B 提交待转述内容和简短原因，在 B 的工作轮成功结算后投递。目标由服务端从委派推导。只产生一份内部交接和一个待处理回合；A 忙时排队。A 的调用沿用原会话的模型、提示词和前缀。转述重试只消费同一份结果。 |
| B 需要用户输入 | 复用待答问题和回答路由，在 A 的会话显示提问者 B 和回答入口。关联原问题 ID、委派及有权答复的人。用户定向答复后只恢复 B。重复点击、过期问题、其他会话或其他人回答由服务端校验。B 收到回复后可继续工作并走上面任一结算路径。 |

直答是普通终态。B 无需在每轮开头或结尾填一份「直答／转述」必选表。当 A 仍需判断、整合材料或完成后续动作时，B 可以请求转述。协作详情保留原因，便于复核模型是否把此入口用成惯例。执行失败、超时、无有效正文或产物时，应投递带原因和实际状态的简短结果，避免把运行时诊断当成功答复或额外调用 A 撰写失败通知。

## 历史、上下文与恢复

- **会话与作者分开存。** 一条可见记录同时关联 A 的来源线程、原请求、实际作者 B 和交付 ID。按实际到达顺序追加，在 UI 中能跳到原问题。来源线程的标题或最新活动 bot 都不能代替委派保存的目标。署名和引用在刷新、手机布局以及历史记录中一致。
- **直答与转述使用同一份事实。** 直答正文以「B 报告」进入 A 的下一次实际调用；内部转述以同样的来源送入明确排队的 A 回合。按交付 ID 协调历史重放和未读注入，避免原文进入两次。检查 API 型驱动的历史重放、原生会话复用、重启重建和摘要压缩；摘要应能区分用户授权、A 的判断与 B 的报告。A 已在生成时，不追改已发出的输入。
- **可靠投递。** 在运行时持久化交付意图、目标和稳定 ID，再把记录写入聊天存储。按委派及对应事件生成唯一标识，问题使用各自的问题 ID。跨存储时以可重放的投递记录衔接：写入聊天前崩溃可重投，写入后尚未确认时可查重。转述结果发布、生成通知及恢复 A 都使用可查重的记录。若 A 已开始转述后崩溃，可重新生成未提交的答复，对用户最多提交一次，不重新执行 B 的工作。
- **执行与表达分开结算。** 分别记录 B 的工作状态、投递状态、转述状态。A 转述失败时先向原会话补发 B 的结果，用户仍可单独重试转述。文件使用已有交付机制，由接收端授权读取。失败、撤销和取消后迟到的结果均不能意外唤醒 A 或产生第二条终态回复。

## 实施顺序

| 阶段 | 工作与交付条件 |
| --- | --- |
| 1．绑定与契约 | 定义单向关系、保存和读取接口、设置选择器、来源快照与可达性复核。用旧配置、解绑及跨会话用例证明作用域。明确与普通工作、咨询、通知和外部轮询的区别。 |
| 2．异步运行与直答 | 处理派发回执、父子结算、通知、未读、原会话可继续输入以及父任务恢复判定。前后端共享消息来源和交付字段。优先跑通无第二次 A 调用的完整路径。 |
| 3．通知 A 和定向问答 | 接入仅对当前委派可用的转述动作、A 的异步回合、B 的问题卡和精准回答路由。UI 完成协作详情、来源跳转、失败状态和附件处理。桌面、窄屏及简单／高级模式遵循项目交互规范。[UI 规范](../../DESIGN.md) |
| 4．恢复与发布验证 | 在隔离服务上注入崩溃、取消、重复事件和权限变更。用受控 provider 捕获实际请求和调用顺序，浏览器走完整交互。运行相关回归、类型检查和国际化检查。实施与验证完成后迁移到 finished_plans 并更新索引。[项目验证入口](../verification/README.md) |

## 验收用例

| 场景 | 要观察的证据 |
| --- | --- |
| 普通聊天；只委派一次 | 普通聊天只有 A 调用。绑定场景中 A 获得受理回执后可结束；B 直接交付触发的 A 调用为零。捕获 provider 请求和运行时事件分别计数，工具执行中的多次 HTTP 请求不能误计为多个会话回合。 |
| 用户在 B 工作期间另问一件事 | A 可以接着答。B 后到的结果仍指回旧请求。用户接着追问结果时，检查实际输入中有一份标明 B 的正文。 |
| 明确转述；A 正忙或转述失败 | 转述成功时主会话展示 A 的最终正文，详情保留 B 原文。失败或空答时主会话自动补发 B 的结果。正常路径只为这次转述安排一个 A 回合。重试和重启均不使 B 再执行或重复发布正文。 |
| B 署名提问 | 定向回复投给正确问题并只恢复 B；普通新消息继续给 A；相同问题被回答两次、过期回答及冒用他人回答均有确定结果。 |
| 长结果和附件 | 用超过旧活动预览长度的答案、仅含产物的答复和无权读取的附件验证正文完整性、作者及文件访问。 |
| 取消、停机与竞争 | 在入队后、B 结算后、消息已写而投递未确认、A 转述中分别中断并重启。核对可见消息数、通知数、恢复次数。验证解绑后在途任务、失去权限和来源线程删除。 |
| 范围回归 | 未绑定协作、咨询、群聊、嵌套委派、外部轮询保留各自的恢复与交付规则。不同会话、分支和人员的结果不能串入。 |
| 模型使用倾向 | 用代表性的直答、点名 A 转述、明确缺资料三类提示分别观察 B 的实际动作。脚本桩验证状态机；真实模型抽样记录额外 A 回合和转述原因。模型若频繁转述普通结果，优先调整工具可见范围和文案，避免重新引入每轮模式选择。 |
