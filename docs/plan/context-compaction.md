# 会话上下文压缩策略

## 目标

聊天消息、工具活动和附件引用继续保存在原有会话记录中。每一轮从有权访问的数据
生成有预算的模型上下文。压缩结果只服务于同一会话和分支，供恢复和继续任务使用。
群聊沿用单聊的持续会话结构，每个 bot 在每个群线程独立续接，本轮输入只带群聊增量。

## 现状

| 路径 | 当前行为 |
| --- | --- |
| 单聊压缩 | 达到模型上下文预算或手动触发时，总结较早历史，保留有界的近期原文。摘要记录绑定分支和消息锚点。重建时默认回放预算为 24,000 字节，摘要上限为 6,000 字节。 |
| 单聊空闲摘要 | 部分长会话会在空闲时提前压缩。Claude Code 可以在原生会话的分支中执行压缩，宿主也有自己的摘要路径。 |
| 群聊默认路径 | 每次从当前房间线程取最多 30 条可读记录，带发言人拼成一段输入。限制按条数计算。若驱动复用原生会话，完整窗口还能被追加到已有上下文。 |
| 群聊重置 | 手动触发或触及阈值后，下一轮启动新会话并发送近期窗口。默认阈值为模型窗口的 90%。 |
| 群聊增量续接 | 默认关闭，目前只覆盖符合条件的 Claude Code 会话。同一引擎实例上有其他 bot 发言后，原 bot 再发言会回退到完整窗口。这是现有实现的限制。 |

参考 [单聊重建](../../server/context-rebuild.ts)、[群聊窗口](../../server/host/room-transcript.ts)、
[群聊会话](../../server/host/room-sessions.ts) 和
[现有压缩验证](../verification/context-compaction.md)。

一轮群聊可以表示为 `system = 当前 bot 的指令`，
`user = 带发言人标签的房间窗口 + 本轮任务`，`assistant = 当前 bot 的回复`。
窗口从第 1–30 条滑到第 2–31 条时，重叠内容的起点也变了。当前时间放在群聊文本前，
换分钟还会改变前缀。同一原生会话内追加完整窗口则会重复纳入已经看到的内容。
这两种开销分别要看缓存命中和实际上下文长度。

## 目标策略

### 上下文预算

- 从现有消息库按线程、分支和受众取数据。固定的身份、指令和工具定义继续走稳定前缀。
  引擎支持时，把当前时间等每轮变化的内容放到可复用文本之后。附件状态和本轮任务随
  动态输入发送。只读 bot 资料沿用 [MEMORY.md 注入方案](read-only-memory.md) 的单独预算。
- 单聊和群聊共用预算计算和 UTF-8 安全截断。按模型窗口扣除当前指令、工具定义、回复
  和后续工具调用所需空间。先设硬字节预算，有可信的上下文 token 读数时用它校验和
  触发压缩。群聊保留条数上限作为第二道边界。具体字节配额由隔离基准确定。
- 优先给当前用户请求、必要附件引用、待处理协作结果和近期原话留空间。历史条目按
  预算选入。超长条目可保留可读片段、来源和消息 ID，完整内容仍可按权限查询。

### 单聊

沿用现有压缩记录和回放机制。可信的原生会话可续接时只发送新增内容。
需要重建时，使用当前分支有效的摘要、近期原文和当前请求。编辑、回退或分支变化后
重验摘要锚点。摘要保留任务决定、约束、未决问题和必要引用，作为历史记录呈现。
模型不可用或压缩失败时，继续使用有界原文回放。空闲摘要和原生压缩按实测收益再调整。

### 群聊

每个「群线程 × bot」持有自己的原生会话和已见消息记录。续接沿用持续的
`system → user → assistant → user …` 历史。同一群里的其他 bot 发言和用户发言，
以带发言人标记的增量加入本轮 `user`，并附上本轮任务。当前 bot 自己上一轮的回复
已经在该会话的 `assistant` 历史里，已见记录也要包含对应的群消息 ID。

例如开发 bot、测试 bot、开发 bot 依次发言，第三轮恢复开发 bot 自己的热会话：

```text
system     开发 bot 的指令
user       Alice：这个版本能发布吗？
assistant  开发 bot 的上一轮回复：构建通过，等测试结果。
user       本轮新增：测试 bot：冒烟测试通过。
                      Alice：@开发 bot，可以发了。
assistant  开发 bot 的本轮回复
```

| 情况 | 发送方式 |
| --- | --- |
| 当前 bot 的会话可验证续接 | 只补它未见的消息和经确认的更正。中间有其他 bot 发言时，仍续接当前 bot 自己的会话。 |
| 当前 bot 首次发言、权限变化或会话失效 | 从有权限的房间记录组装一份有界窗口，在干净的模型上下文中发送。 |
| 续接失败、增量超出预算、消息变更无法校验、达到压缩阈值或手动重置 | 作废当前 bot 的已见记录，用当前有界窗口重建它的会话。 |
| 很长的项目讨论需要近期窗口之前的细节 | 先通过历史会话搜索查原文。实测出现持续遗漏后，再评估房间摘要是否值得增加。 |

续接沿用现有消息 ID 和内容校验机制。把已见记录绑定到实际接受输入的原生会话，
在发送结果可确认时更新，失败或重试时以可验证的记录为准。引擎进程可以复用或退出，
重新启动进程后，只要能恢复当前 bot 的原生会话并验证其状态，仍然发送增量。
完整窗口回退由驱动明确开始新上下文。按引擎逐个验证，优先覆盖现有 Claude Code 路径，
并记录每轮采用增量、全量重建还是手动重置。

## 实施与验收

1. **先量基线。** 在隔离服务中跑同一 bot 连续答、两个 bot 交替答、长消息和手动压缩。
   记录每轮发送的群聊字节数、实际输入和缓存读写 token、上下文占用、重建次数、
   首 token 延迟。缓存数据和延迟只在提供方实际报告时用于判断收益。
2. **先做群聊预算和回退。** 验证 30 条长消息时仍能送达当前请求，中文和附件引用
   保持可用。检查完整窗口回退后，驱动不会继续累加同一窗口和旧会话内容。
3. **验证交替发言再扩大覆盖。** 在同一引擎实例跑 `开发 → 测试 → 开发`，检查开发 bot
   第二次发言时的会话 ID 和本轮输入。它应继续使用上次会话，只收到中间新增的群消息，
   自己的旧回复仍在原有 `assistant` 历史中。再验证消息更正、重启、超时、失败重试、
   自动压缩和权限变更。对照实际引擎输入，确认消息覆盖与访问范围。
4. **回归单聊和会话数据。** 验证摘要能恢复正确分支，最近原文和待处理任务完整，
   压缩前后的原始历史及搜索结果均可访问。按 [隔离验证流程](../verification/README.md)
   在正常入口验证，再用同一组场景比较前后的 token 与延迟。
