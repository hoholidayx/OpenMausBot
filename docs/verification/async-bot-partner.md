# 私聊工作搭档验收

本次验收日期为 2026-11-19。A 是用户所在私聊的 bot，B 是 A 在设置中单向绑定的工作搭档。[设计与范围](../finished_plans/async-bot-partner.md)

## 用户可见的行为

验收以原会话是否收到实际结果为准。B 的直答和 A 的转述都满足要求，点名某位 bot 发言属于表达偏好。

- 在简单或高级模式的 bot 设置中打开「工作搭档」，选择、替换或清除一个可协作的 bot。修改影响后续派发。已受理的工作继续跟随原用户请求，实际投递时再次检查权限。
- B 正常完成后，A 的原会话收到一条署名 B 的答复，可带文件。用户另开话题时仍由 A 回答。下一次调用 A 时，历史会标记结果来自 B。
- B 在自己的委派中调用 `request_partner_relay` 并给出原因时，服务端等 B 成功完成后再安排 A 转述。主会话保留 A 的最终答复，从委派回执可以进入 B 的工作线程查看材料。转述报错或成功结束却没有可见答复时，服务端自动补发 B 的原文与可交付附件。A 报错时，用户仍可用「重试转述」重新调用 A。
- B 的问题卡显示在 A 的会话中。卡内回答或针对卡片的文字回复送到 B 的原任务。普通输入继续交给 A，权限审批继续使用原审批通道。

## DeepSeek Flash 真实模型

在独立数据目录中创建 Atlas 和 Juniper，使用 OpenCode Go 的 `deepseek-v4.1-flash`，经本项目的 OpenAI 兼容驱动调用。参考同级 Novia Server 的历史验证材料 `tmp/02h-live-1736AM/validation.json`，取其中雨天喝茶、Mac mini 上的 cloudflared 更新、今晚仍在使用等情境，重新组合为只做纸面分析的请求。模型回合按委派运行时的执行次数统计，同一回合中的多次工具往返合计一次。

| 输入及条件 | 实际交付 | A / B 回合 |
| --- | --- | --- |
| 自然语言要求 Juniper 直接给出建议，今晚先别重启 | A 的原会话收到署名 Juniper 的建议，B 完成后 A 额外调用 0 次 | 1 / 1 |
| 自然语言要求 Juniper 交材料、Atlas 转述 | Atlas 承诺转述，Juniper 实际选择直答。用户在原会话收到了结果，发言者与偏好有出入 | 1 / 1 |
| 同类任务，在验收输入中点名转述工具 | Juniper 登记转述原因、完成材料，Atlas 随后整合。主会话未出现单独的 B 结果正文 | 2 / 1 |
| 缺少维护窗口，让 Juniper 在原会话询问并等待 | 真实问题卡显示在 Atlas 会话。定向回答「周六北京时间凌晨两点，最多十五分钟」后，Juniper 给出 02:00 开始、02:15 前恢复的方案 | 1 / 1，同一 B 回合从原生提问工具继续 |

首轮缺资料样本中，旧的完全访问策略在服务端截获 B 的真实提问工具，导致它自行假定 60 分钟。复现后把已绑定的私聊工作委派接回用户答题路径；普通委派保留其提问策略。另一个可复现的问题是长正文被交付链裁到 12,000 字符，已用超过 15,000 字符的实际聊天消息核对完整性。

发布复测再次收到一条署名 Juniper 的建议，Atlas 和 Juniper 各执行一次。模型仍会把原会话描述成「收件箱」。表中的自然语言转述偏差与这些表述均作为质量观察保留。任务材料、人物名和运维偏好均未写入产品提示词。

## 隔离回归

发布前先重现转述失败和空答时缺少实际结果的问题，再用相同用例验证自动补发。工作搭档、运行时、问题路由、上下文、附件与工具桥共 17 个相关测试文件，434 项通过。类型检查、lint、变更检查、16 种语言目录校验，以及 Web、服务端和文档站生产构建通过。运行以下用例可重新创建临时 bot、聊天数据库和受控模型。测试通过真实 HTTP、工具桥和持久化的委派记录核对运行次数。

```sh
pnpm exec vitest run server/work-partner.e2e.test.ts
```

| 检查 | 观察点 |
| --- | --- |
| 工作中继续聊天、期间解除绑定 | 即使开启「等待队友时暂缓私聊」，用户也能先与 A 聊其他事。B 的晚到结果引用旧请求，后续给 A 的实际输入只包含一份带作者的结果。 |
| 长答复和仅附件结果 | 验证完整正文、实际作者、CSV 附件和下一次输入中的文件名。附件继续使用已有的交付与访问检查。 |
| 转述失败 | 让 A 报错或返回空白，验证用户无需重试就可看到 B 的结果。只含附件的结果在重启补投后仍只出现一次。用户手动重试时 B 的执行次数仍为 1。 |
| 中断与恢复 | 在隔离服务进程退出后，用原数据库重启。覆盖 B 已结算尚未投递、直答已写尚未确认、A 正在转述、A 的转述已提交尚未结算、B 的问题尚待回答。核对投递条数、已提交答复及 provider 回合数。 |
| 取消和权限变化 | 显式停止原请求或让工作搭档失去可见性，再释放 B。运行记录保留取消或未送达状态，原会话不出现晚到正文。 |
| 来源分支 | 通过 HTTP 把原消息编辑成新分支，委派 B 后切回另一分支。即使 B 请求转述，原分支也立即收到一份带署名的结果，另一分支的末尾保持原样。源消息已删除时跳过写入。 |
| 浏览器 | Chrome 验证简单模式绑定、高级模式读取与清除。通过桌面问题卡回答。另一次让 A 转述报错，在点击重试前看到 B 的原文和署名。两种场景均在 390 px 窄屏刷新后核对。 |

更广的回归中，两个旧用例在限制原生 bot 加入群聊的检查处失败，另有两个旧 MCP 工具说明断言失败。这四项在本次修改前的 `e481f4a8c` 快照上也能复现，此处单独记账。真实模型样本用于说明可达路径和已观察到的偏差，无法估算模型选择不同出口的成功率。

## 本机部署

通过项目管理脚本重启本机 Web 服务，启动命令退出后再次检查进程和监听端口。主服务的 `8799/api/health` 和 webhook 的 `8800/health` 均返回 HTTP 200。实际首页引用的两份 JavaScript 和一份 CSS 与本次生产构建的 SHA-256 一致。浏览器和模型的写入验证均在独立数据目录进行。

## 排查输出截断

本机 Web 部署可按事件名查看记录，再按 `threadId`、`turnId` 或 `assignmentId` 关联同一次请求。

```sh
rg 'output_truncation' ~/.openmausbot-service/web.log
```

- `stage=provider` 表示 OpenAI 兼容聊天回合收到了上游的输出上限信号。Chat Completions 记录 `length`，Responses 记录 `max_output_tokens`。日志包含模型、回合 ID、该回合内的请求轮次和已收到的正文长度。上游提供输出 token 用量时一并记录。
- `stage=turn-outcome` 表示服务裁剪了本轮向协作运行时传递的副本。`stage=assignment-result` 表示裁剪发生在委派结果入库时。两者都记录裁剪前后的 UTF-16 长度。原聊天气泡可以保留更长的正文。
- 这些事件只在收到输出上限信号或实际发生本地裁剪时产生。排查历史请求须核对当时运行的服务版本。日志字段不包含答复正文、推理或工具参数。
