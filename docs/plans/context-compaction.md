# 单聊和群聊的上下文

## 群聊准入

只有逐轮发送显式对话历史的 API 驱动可作为群聊成员。准入按 provider instance 的驱动决定，同名模型走不同驱动时可以有不同资格。Codex、Claude Code、ACP、Pi 等持有原生会话的驱动使用单聊。部门和共享指令沿用原有规则。原生 Chief 可以通过管理列表编辑本部门且在可见范围内的房间。

房间显示、接话人选择、发送、队列和协作工具使用有效成员列表。升级前已有的原生 bot 成员 ID 在派发与成员展示中跳过，旧权限范围继续约束原有内容。房间原文可以查看和搜索，失去所有有效成员的房间提示添加 API bot。日程生成群聊时同样校验成员。

通过 `coordinate_bots` 可以从房间把独立任务交给原生 bot。它在自己的单聊线程中运行，只接收显式任务说明、转交的文件和其本有权读取的单聊上下文。协调器把结果返回发起任务的房间。消息可见性、部门范围与文件转交仍由原有的授权逻辑判断。

## 逐轮发送

API 单聊与群聊使用同一个宿主压缩器。群聊按「线程 × bot」读取当前活跃分支。当前 bot 的历史回复按 `assistant` 发送，其他发言按 `user` 发送并保留发言人。当前轮所需的群消息作为一个有序增量进入末尾 `user`，上一轮的独立消息保留原有角色。API 每次请求都重发有效历史前缀，当前任务、时间和动态提示放在末尾。

```text
system     开发 bot 的固定指令、部门指令和房间公告
user       Alice：这个版本能发布吗？
assistant  开发 bot：构建通过，等测试结果。
user       测试 bot：冒烟测试通过。
           Alice：@开发 bot，可以发了。
assistant  开发 bot 的本轮回复
```

原生单聊保留引擎游标和发送确认，游标有效时发送新增内容。引擎原生压缩事件更新提示和用量，不清理有效游标。失去游标后按有界原文回放恢复。旧宿主摘要继续作为历史记录展示，回放时跳过。已经使用过旧宿主摘要的原生会话在下次发送时从原文重建。手动压缩入口说明原生引擎自动管理上下文。

## 递归摘要

- 压缩从活跃分支和当前 bot 有权读取的历史获取数据。最近 `N` 条发言默认按实际用户或 bot 文本计数。当前输入、必要附件和待处理协作结果保留。模型调用期间的工具请求和结果仍由驱动成对传输。
- 摘要使用 **上版有效摘要和本次切点前新增的旧消息**。超长历史按时间顺序和字节预算分批，每批带上已生成的摘要。使用同一 provider instance 和模型的无工具文本请求，提取项目约束、决定、任务进度和必要引用。摘要上限为 6,000 UTF-8 字节。
- SQLite 为每个「线程 × bot」保存最近一版摘要、覆盖消息 ID、前缀指纹和权限范围指纹。生成完成后复核分支、前缀和权限。新摘要在历史前缀中注入一次，供模型参考。聊天仅显示完成标记。切换分支、开始新上下文、撤销成员或删除线程时清理相关状态。普通重启后复核后复用，工作区备份保留原始会话。
- 未能生成时沿用仍有效的摘要，并在预算内回放近期原文。超出的历史有明确的省略或节选标记。本轮必需内容超出窗口时提示缩短请求或移除附件。原始会话、附件、历史搜索和只读 `MEMORY.md` 独立保存。

| 配置 | 行为 |
| --- | --- |
| `context.compactAt` | token 数阈值。低于 1 时为窗口比例。默认 80%，最多按窗口 90% 计算。 |
| `context.keepMessages` | 最近发言数量，默认 12。 |
| `context.autoCompact` | 默认开启。控制发送前压缩和空闲压缩，手动压缩单独可用。 |
| `context.idleCompact` | 默认开启。达到同一阈值后延迟 10 秒尝试。正在运行、续接或排队的会话由前台路径处理。 |
| `context.rebuildBytes` | 有界回放预算，默认 24,000 字节。原生恢复及宿主压缩失败后的历史回放使用此预算。 |

预算优先使用当前模型和请求前缀对应的实际上下文占用，加减本次请求相对上次的估算差量。缺测时估算包含固定指令、历史、动态内容、工具定义和图片的完整请求。多轮工具调用累计消耗单独计账。

空闲、手动和发送前压缩共享同一任务入口，同一个 bot 在同一线程最多运行一个摘要任务。新一轮超出阈值时可等待已有任务或启动一次前台压缩，总等待至多 20 秒。Stop、退出、分支切换和权限变化会取消任务或拒绝晚到的结果。

旧群聊原生游标表、独立群聊阈值和 Claude 空闲分叉压缩已退出派发链路。提示缓存保温与原生压缩事件继续由各自的机制处理。验证命令和覆盖范围见 [上下文验证](../verification/context-compaction.md)。

## 后续改造

### 优先处理

1. **超长重试保留本轮必需内容（已实现）。** API 聊天的普通 MCP 文本结果使用 8 KiB 预览，长结果尽可能沿用已有的工作目录存档。供应商拒绝超长请求时，驱动优先缩短工具输出，再裁普通旧消息，保留调用 ID、执行状态、可回读文件和预检标记的必需消息。重试仍放不下时沿用超长提示。已用模拟供应商验证重试能保留当前输入和协作结果，并核对连续大工具结果的配对和文件引用。
2. **长历史的摘要分批保存进度。** 所有批次共用 20 秒上限，当前只有全部成功才保存。第二批失败会让后续发送从第一批重来。每次限制处理批数，成功一批就复核分支、覆盖前缀和权限后保存切点。失败后使用有效摘要和有限原文继续普通发送，并短暂延后自动重试。验收时让第二批失败，确认下一次从上次成功的切点继续，已处理原文不会重复送去归纳。

### 随后验证

- **群聊缓存前缀。** 多条群消息在本轮合并为一条 `user` 消息，下轮回放会拆开，导致之前发送的包无法匹配。按线程和 bot 保留实际送出的分组，用连续请求检查历史前缀的一致性，并用供应商返回的缓存用量评估收益。
- **小窗口、缺失用量和多轮工具调用。** 未知模型窗口时默认按 128k 估计。发送前预检只看到初始请求，后续工具结果会继续增长。用较小实际窗口、有无真实用量交替的响应和长工具结果验证预算与重试。
- **长会话性能和存储。** 摘要只缩短模型输入。原文、搜索索引和备份仍随对话增长，活跃分支读取和摘要指纹校验还会扫描旧历史。先测长会话的发送前耗时和备份体积，再评估怎样减少旧历史的重复读取和校验。
