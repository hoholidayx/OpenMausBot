# 单聊与群聊的会话上下文策略

## 目标

单聊和群聊共用一套宿主上下文处理流程，统一管理模型会话续接、已见记录、用量、递归摘要和恢复。
群聊中的每个 bot 在该群线程内拥有一份独立上下文，使用与单聊相同的策略。原始会话、分支、工具活动和
附件仍由会话库保存，历史搜索继续查原文。`MEMORY.md` 仍由现有只读入口独立注入。

## 现有链路

| 路径 | 当前实现 |
| --- | --- |
| 单聊 | 发模型请求前由宿主判断是否压缩。有效的上一版摘要已经会进入下一次摘要的输入。自动压缩默认留两轮交互，手动压缩尝试摘要所有当前历史。重建默认回放 24,000 字节，摘要上限 6,000 字节。记录以消息锚点校验分支。 |
| 用量 | 单聊默认在 80% 窗口触发，优先使用适配器报告的最近一次 prompt 占用，其次估算历史文本字节数除以 4。估算没有覆盖下一轮完整输入。ACP 的 `usage_update` 目前只给表盘使用。Claude 的已知原生阈值还会下调宿主阈值。 |
| 空闲压缩 | 完成一轮后可安排宿主压缩，或在 Claude Code 分叉会话中跑原生 `/compact`，成功后切换原生会话。现有调度依赖引擎类型、缓存和忙碌状态，另有提前触发阈值及最长三分钟的前台等待。 |
| 群聊 | ACP、Codex 和支持可靠续接的 Claude Code 按「群线程 × bot」保存原生会话和已见位置。各自续接时只发送新增消息，失效时按预算回放原文。对由宿主管理压缩的引擎，手动请求或达到 90% 默认阈值时重置目标 bot。 |

## 单聊与群聊统一后的目标

上下文按「线程 × bot × 分支」隔离。每份上下文记录自己的有效摘要和覆盖边界、原生会话游标、
已见消息以及最近一次可信用量。使用游标前还要核对适配器、模型、会话和受众。群聊成员共用一份
房间消息记录，各自保存自己的上下文状态。换另一个 bot 发言后，之前 bot 的上下文仍可按原游标校验。

单聊和群聊都从消息入口取得当前 bot 有权读取的记录，再调用同一套预算判断、压缩、发送和确认逻辑。
单聊入口提供该线程的历史和本轮请求。群聊入口提供可读的群消息，附上发言人标记，再补上本轮任务。

| 会话状态 | 两种聊天共用的行为 |
| --- | --- |
| 原生会话可校验续接 | 本轮 `user` 只补尚未确认接收的可见消息和本轮任务，历史 `assistant` 仍在原会话里。 |
| 首次发言、压缩完成或游标失效 | 在干净会话中加载有权使用的有效摘要、近期原文和本轮任务。无有效摘要时使用有界原文。 |
| 无状态模型接口 | 发送显式组装的完整有界上下文，按角色保留稳定历史和本轮 `user`。 |
| 发送确认、失败或重试 | 以实际接受输入的会话为准推进已见边界。同一批消息可以用于干净会话恢复。 |

固定指令留在稳定前缀。时间和本轮任务等动态内容跟随当前增量。进程重启、引擎自身发生压缩
或读取权限变化时，按同一规则重验状态。恢复仅重建当前 bot 的会话。

### 递归压缩

以下流程适用于由宿主负责压缩的引擎。

1. 从当前分支、当前 bot 有权访问的记录选出压缩切点。最近 `N` 条可回放聊天消息按用户或 bot 的实际发言计数，压缩提示、工具活动和内部摘要记录不占名额。切点落在仍需配对的工具交互中时，将这组记录一起留在近期区间。本轮尚未执行的输入、待处理的协作结果及必要附件引用也单独保留。
2. 取 **上一版有效摘要 + 上次覆盖位置到本次切点之间的新增旧消息**，让无工具的文本调用生成下一版摘要。旧消息多到单次请求装不下时，按时间顺序分批，每批带上一批的摘要。摘要有独立的输入和输出上限，只保存任务目标、项目约束、决定、进度、未决事项和必要引用，并标清已撤销的决定及信息来源。
3. 成功后提交新版摘要及覆盖到的消息 ID。新摘要替代上一版在请求中的位置，日常续接不会反复注入。摘要是会话历史资料，当前工作区规则、bot 指令和有效的用户更正仍按既有优先级生效。
4. 超时、模型不可用或返回无效内容时，保留上一版有效摘要和覆盖位置，按硬预算回放近期原文。缺失的区间明确标示，可从历史搜索找回。若近期原文仍超出预算，优先保留本轮请求及必要引用，对超长历史条目做 UTF-8 安全节选。若本轮请求本身装不下，明确返回可处理的错误。

提交前复核覆盖区间、消息版本及上下文归属。编辑、回退、删除、撤权或清空上下文使受影响的摘要和原生游标失效。重启后只恢复可校验的已提交状态。原有摘要标记留作历史显示，新摘要版本按需从原始记录建立，尤其避免旧记忆回流。

### 阈值与用量

| 配置 | 首版建议 |
| --- | --- |
| `context.compactAt` | 沿用比例或 token 数，默认 80%。单聊和群聊共用，受实际窗口、回复和工具所需余量限制，也为已知的更低原生压缩阈值留余量。 |
| `context.keepMessages` | 保留最近原文条数，建议起点 12 条。长消息、中文及工具交互样本会用于校准，字节和 token 安全预算优先。 |
| `context.autoCompact` / `context.idleCompact` | 复用现有总开关，新增空闲开关。关闭空闲压缩时仍可在下一轮发送前压缩，关闭自动压缩时仍可手动压缩。发送前的窗口容量检查始终执行。 |

优先采用**模型服务端返回的、对同一原生会话和模型仍有效的实际上下文占用**。例如 Claude Code
的最近一次 prompt 包含未缓存输入、缓存读和缓存写，Codex 使用最近一次调用的输入。加上上次读数
未覆盖的回复和待发增量，并为当前动态指令、工具定义、附件及输出留预算。整轮多次调用累计的
input tokens 只用于用量记录。换模型、换会话、切分支、原生压缩或缺测后，应重判读数是否有效。

没有可信读数时，在本机对这次请求会占用的完整上下文计数。原生续接也要估算已确认接收的历史，
再加本轮增量。能使用对应模型 tokenizer 时直接计数，否则用对中文、代码和结构化内容留余量的
保守估算，并保留字节上限。没有窗口报告时沿用模型目录和现有回退规则，标出估算来源。

ACP 的原生会话由后端自行压缩，单聊使用 `usage_update` 显示占用。宿主的发送前压缩、空闲摘要和
手动压缩仅适用于宿主管理压缩的引擎。已有宿主摘要继续显示在聊天历史中，ACP 续接原生会话时
跳过这些摘要，原生会话丢失时按预算回放原文。

### 空闲与前台等待

- 一轮完成且达到同一个自动阈值时，可在会话空闲后排一个摘要任务。首版用短延迟和单次执行，保留忙碌、退出、删除及 Stop 的取消出口。与发送前压缩和手动压缩共用同一个生成、提交入口。
- 如果下一条消息先到，按现有接收与排队方式保留消息。发送前仍够空间时可以正常发，取消或作废未提交的空闲任务。需要压缩时等待正在运行的同一任务，或启动一次前台压缩。摘要以入队消息之前的已完成历史为输入。
- 等待使用现有忙碌状态，首版可沿用宿主摘要的 20 秒超时，并将其作为一次前台发送的总等待上限。超时走有界回放。Stop 或切分支取消对应任务，晚到结果不得覆盖当前状态。同一切点最多提交一次，保留现有预算限制和摘要调用的访问授权。

### 群聊续接示例

开发 bot 与测试 bot 交替发言时，开发 bot 恢复自己的会话。它自己的回复已在
`assistant` 历史里。测试 bot 和用户此后新增的发言进入本轮 `user`。

```text
system     开发 bot 的指令
user       Alice：这个版本能发布吗？
assistant  开发 bot：构建通过，等测试结果。
user       本轮新增：测试 bot：冒烟测试通过。
                     Alice：@开发 bot，可以发了。
assistant  开发 bot 的本轮回复
```

开发 bot 达到阈值、在空闲时归纳或收到手动压缩请求，均按上述流程更新自己的摘要。测试 bot 保留
自己的游标、用量和摘要。群里积累的未见消息一次装不下时，当前 bot 也按相同预算先压缩，再重建。

## Hook 和旧链路取舍

| 决策 | 接口及理由 |
| --- | --- |
| 保留用量与调度入口 | `thread.token-usage.updated`、`turn.started`、`turn.completed` 分别用于计量、取消旧空闲任务和排新任务。保留 Stop、会话忙碌及队列、删除和关闭时的生命周期边界。 |
| 保留原生事件 | Claude 的 `PreCompact`、`SessionStart(source=compact)` 与 `context.compacted` 继续识别引擎自身的压缩边界，重验占用和已见记录，并保留必要的 digest 补发与可见状态。保留 `PostToolUse`、`PostToolUseFailure` 的工具结果、安全和错误处理。 |
| 保留恢复接口 | `session.started`、`resumeCursor`、`sessionReset`、`recoveryText` 和 `Handoffs` 的发送确认。保留权限判定、回复引用、待处理协作结果、UTF-8 截断、会话原文和搜索。 |
| 保留手动入口 | `POST /api/bots/:id/compact` 和 `POST /api/groups/:id/members/:botId/compact` 为宿主管理的引擎接入同一压缩器，为 ACP 返回 `409 provider_managed_context`。保留上下文表盘、进度和结果提示。宿主管理的群聊在读数缺失时按可见历史估算。 |
| 替换旧压缩策略 | 用统一的阈值、近期保留和等待策略取代单聊专用切片、空闲原生 `/compact` 分叉及群聊只清游标的压缩。独立的提示缓存保温功能继续按自身设置运行。 |
| 退役旧配置和路径 | 新链路只使用通用 `context.compactAt`。升级时提示将旧 `roomCompactAt` 中仍需要的值显式迁到通用配置，因为通用值也作用于单聊。各引擎验证冷启动、重连和增量后，清理群聊旧调度及整窗续接分支。 |

## 群聊增量续接

群聊统一从当前活跃分支组装请求。SQLite 只留每个「群线程 × bot」的最近一份确认记录。
一轮成功完成且回复落库后保存已确认位置，下一轮派发前消费该记录。同一引擎的多个 bot 沿用现有进程池，
轮到某个 bot 时加载它自己的原生会话。校验同时覆盖已保存游标和正在发送的其他群线程，防止两个线程认领同一原生会话。

普通服务重启可续接已确认的会话。Stop、超时、未完成的轮次、分支变更或权限校验失败时，从当前分支恢复。
工作区备份保存原始消息，恢复后用原文建立新的群聊会话。原始消息继续供历史搜索使用。

原文回放取最近 30 条，并服从 `context.rebuildBytes`（默认 24,000 字节）。
本轮请求、必要附件引用和待处理协作结果单独保留。旧 `context.roomSessions` 和
`OMB_ROOM_SESSIONS` 已退出发送决策。当前群聊阶段沿用现有用量与重置策略，ACP 的压缩继续由后端负责。
参见 [群聊续接验证](../verification/context-compaction.md#rooms)。

1. 在隔离实例记录单聊和群聊的输入及缓存 token、摘要耗时、前台等待、首 token 延迟和重建次数。
   覆盖长中文、代码、附件和工具交互。
2. 为宿主管理的引擎接入共用的递归摘要、阈值、近期保留和等待策略。验证三次连续压缩、有读数与缺测、
   过期读数、小窗口、空闲和手动压缩。

   确认原文和搜索结果可读、群里多个 bot 各自推进后，再退役旧调度和配置。
